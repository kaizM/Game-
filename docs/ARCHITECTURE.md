# Harborlight architecture

## Current implementation

- **Unity client:** Unity 6.5.4f1, URP 17.5.0. `Assets/Scenes/Harborlight.unity` contains the runtime bootstrap. `HarborlightBootstrap` creates world geometry, materials, vehicles, residents, camera, HUD, and touch controls.
- **Static world:** `HarborlightBootstrap` and `HarborlightDistrictSurfaceNetwork` generate a 6,000-by-4,116-meter (24.70 km²) playable map locally on each process. The expanded source builds 23 north–south routes and 26 east–west rows including the core connector, 1,200 outer building shells across ten named areas, three commons/park areas, and 36 road-intersection entry zones. Outer shell visuals use per-client distance loading (450 m in, 560 m out, two spawns per 0.5 seconds); collision boxes stay resident. The terrain grade eases from z=-58 m to z=-800 m; the map runtime smoke passed all 598 generated road crossings, 84 sidewalk probes, and five streamed-building ground checks. The current Mac QA build passed the map layout smoke with 900 unique in-bounds distributed spawn slots and five streaming waypoints; the authenticated two-client avatar-visibility run was on the previous 14.24 km² build. The first eight NGO client IDs retain the starter spawn; later IDs rotate through the entry zones. Server-side avatar interest management starts player objects hidden, then updates visibility every 0.5 seconds using 200 m spatial cells, a 700 m show distance, and an 850 m hide distance. The world stays local to each process; vehicles, NPCs, and world objects are not yet networked or distance-filtered. Full-map traversal, live later-client spawn allocation, far unload/reload, multiplayer movement on the expanded layout, and Android profiling remain open.
- **Local gameplay state:** `HarborlightGameState` owns mission stages, credits/reputation, offline cash and bank transfers, vehicle ownership, tutorial progress, and schema-v9 JSON persistence. It migrates earlier PlayerPrefs and JSON save versions, including v8. Gameplay must continue offline.
- **Character and vehicles:** `HarborlightPlayer` uses a `CharacterController` and switches into a `HarborlightVehicle`; owned vehicle purchases and cosmetic paint are handled by `HarborlightGarageService`. Current driving is local physics/presentation, not an authoritative network protocol.
- **Backend client:** `HarborlightBackendClient` stores a guest-session token and calls the REST API for profile, gems wallet, authenticated cash/bank snapshots and transfers, cosmetics, and source-level inventory catalog/snapshot/purchase/equipment actions. Bank and inventory writes use client idempotency keys; the API remains authoritative. Inventory client code has not been built or run. This does not own the world simulation.
- **Admin adapter:** `game-admin-sdk` exposes a development-only local adapter and an engine-neutral typed REST contract. The production service uses OIDC role/MFA gates and an allowlist, and has no arbitrary SQL endpoint.
- **Service:** `harborlight-services/api` is ASP.NET Core on .NET 10 with PostgreSQL migrations and a restricted runtime database role. The separate server-rendered console is not enabled until OIDC is configured. Azure Bicep exists but has not been deployed.

## Current system boundary

The first realtime player slice is implemented and loopback-tested: direct Unity Transport sessions, a server launch path, an NGO player prefab, server-owned character movement, replicated locomotion state, server-validated interaction acknowledgments, and client reconnect after a server restart. An authenticated two-client Mac loopback verified avatar visibility at 700→900→700 m on the prior 14.24 km² build; the 24.70 km² map has layout-smoke evidence but not a renewed two-client movement run. Account-linking UX, production store verification, AdMob integration, persistent social graph, vehicle replication, and admin control over a live game world are absent. The `com.unity.multiplayer.center` editor package does not itself implement networking.

## M4 multiplayer foundation (verified; production multiplayer incomplete)

The first client-server slice uses Unity Netcode for GameObjects `2.13.3`; Unity `6000.5.4f1` resolves its declared Transport dependency to built-in Unity Transport `6.5.0`. Development launch flags are `-harborlight-server` and `-harborlight-connect <host>`; the server binds to loopback by default and accepts `-harborlight-listen <IPv4>` only when LAN binding is intended. The project has a resident-based network player prefab, server-owned CharacterController movement, owner-checked/rate-limited input RPCs, server-written locomotion replication, distance-validated interaction acknowledgments, and client reconnect with exponential backoff capped at 30 seconds. A bounded Mac development-player smoke verified two connected clients, movement input, locomotion Animator parameter updates, both interaction acknowledgments, and a separate client rejoining a restarted server. It used the same development player binary in server mode; a Unity Dedicated Server target has not been built. Client presentation has no movement prediction yet. Online interactions acknowledge server validation but do not grant job progress or rewards. Offline play remains the default. The existing ASP.NET Core API remains responsible for guest identity, wallet, cosmetics, and durable records; it is not the realtime world process. Account authentication, authoritative progression, online-state restoration after reconnect, Android transport, internet hosting, and production performance remain unverified or unimplemented. See `reports/network-player-prefab-2026-10-17.md` and `reports/network-runtime-smoke-2026-10-17.md`.

The M5 identity bootstrap issues 60-second opaque join tickets from the authenticated guest API. The database stores only a SHA-256 ticket hash and atomically marks it consumed once. The Unity client encrypts the ticket with a configured RSA public key; NGO approval decrypts it on the server, consumes it through the API, and binds the returned stable `playerId` before player spawn. Beacon, courier, and dock-inspection stages and their in-game credit/reputation rewards are processed by the authenticated API with row locking and idempotent action receipts. API tests, an HTTP smoke, and a one-client Mac loopback run verify all eight Unity actions through the API into PostgreSQL; the final values were stages 2/3/3, 425 credits, 4 reputation, one delivery, and eight receipts. Bank transfers and item-inventory purchases lock per-player progress and use shared idempotency plus immutable ledgers. The current API suite passes 24/24 against local PostgreSQL, including bank and inventory cases. Unity source includes an ATM, online bank UI, local offline bank ledger, and an online inventory panel; its inventory UI has not been compiled or exercised in a player. A separate server-restart rejoin still verifies beacon-stage restoration only. Full-chain reconnect, item sales/trading/effects, Android networking, and secure remote transport remain open. The player snapshot is applied after NGO spawn so the initial server update does not mutate unspawned `NetworkVariable`s. Development macOS uses an OAEP-SHA1 compatibility path for the current Mono runtime; other builds use OAEP-SHA256. Client-supplied IDs do not authorize operations.

## Target architecture gates

Before selecting a networking dependency, verify its Unity 6 support, Android client support, dedicated/headless server support, license, transport behavior, operational cost, and upgrade policy. Then separate:

1. **Client simulation/presentation:** touch/keyboard input, interpolation, camera, animation, VFX, and local prediction.
2. **Authoritative world service:** sessions, character state, ownership, jobs, vehicle seats, combat validation, economy, inventory, property, faction roles, trade settlement, and progression.
3. **Relational persistence:** versioned migrations, atomic transactions, immutable wallet ledger, idempotency, audit, and restore.
4. **Operator tools:** OIDC+MFA, role checks, allowlisted typed changes, audit logs, and explicit separation between local development controls and production administration.

Keep guest/offline play intact while online identity, world sessions, and wallet features are added. No client may receive service credentials.
